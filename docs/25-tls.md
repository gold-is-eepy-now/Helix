# 25. TLS 1.3 client and certificate checks

Status: built and tested in QEMU only. HTTPS works against a local test server whose
certificate is signed by a test CA that exists only in the test image. Public internet
sites have not been tested. Not run on real hardware.

## What works

- `fetch https://...` and the desktop Browser open a TLS 1.3 connection, check the server
  certificate, and then send the HTTP request over it.
- The suite (`tests/shell-test.py`) checks:
  - a certificate from the test CA on `https://10.0.2.2:44443/` gives HTTP 200 with the
    expected body length;
  - a certificate from another CA is refused;
  - the Browser shows `HTTP 200, 36 bytes` for the good server and
    `Could not load: certificate refused: no trusted root` for the other one.
- Host interop: OpenSSL 3.0.13 completes the handshake with this client (`tests/tls13-interop.sh`):
  ECDSA-P256 leaf, RSA-PSS leaf, a wrong root (refused, exit 3), and an IP host.

## Pieces

| Part | File | Notes |
| --- | --- | --- |
| TLS 1.3 handshake state machine | `kernel/src/tls13_client.c` | Suite TLS_CHACHA20_POLY1305_SHA256 only; X25519 only; SNI omitted for IP literals. |
| Record layer | `kernel/src/tls13_record.c` | ChaCha20-Poly1305 seal and open. |
| Certificate and CertificateVerify checks | `kernel/src/tls13_verify.c` | Parses the Certificate message (RFC 8446 section 4.4.2); CertificateVerify accepts rsa_pss_rsae_sha256 (0x0804) and ecdsa_secp256r1_sha256 (0x0403). |
| Chain validation | `kernel/src/x509_verify.c` | Name linkage, CA basicConstraints, validity, SAN matching, anchors by DER equality or by subject plus signature. |
| Session (sockets) | `kernel/src/net_tls.c` | Opens over `net_tcp`, sends and receives application data, closes with close_notify. |
| HTTP over TLS | `kernel/src/net_http.c` | `parse_url` accepts https (port 443); send, recv and close use TLS when the scheme is https. |
| RSA verify | `kernel/src/rsa.c`, `bignum.c` | PKCS#1 v1.5 and RSA-PSS (MGF1-SHA256). Montgomery multiplication over 32-bit limbs. |
| ECDSA P-256 verify | `kernel/src/ecdsa_p256.c` | Jacobian coordinates; modular inverse by Fermat; strict DER `SEQUENCE{r,s}`. |

## Refusals (fail closed)

- No RDRAND: HTTPS is refused before any packet is sent.
- No wall clock: certificate dates cannot be checked, so the connection is refused.
- Any chain, name or signature failure: no application data is sent. The reason is shown
  in `fetch` output and in the Browser status line.
- Algorithms other than RSA-SHA256 and ECDSA-P256-SHA256 (including SHA-384 and SHA-512
  chains) are refused by name.

## Test trust anchor

`make test` builds a second kernel with `HELIX_TLS_TEST=1` in `build/tls-test/`. That build
embeds `build/tls-test/ca.der` (made by `tests/tls-test-ca.sh`) through `tools/embed_der.py`.
The release image is built without the flag, and `nm` confirms it has no `helix_tls_test_ca`
symbol. The test leaf has SAN `IP:10.0.2.2` and is served by `tests/tls-test-server.py`
on the host.

## Measured

- Kernel stack frames (measured with `-fstack-usage`): `x509_verify_chain` 3952 bytes,
  `ecdsa_p256_verify_sha256` 3568, `rsa_public_op` 2640, `mont_modexp` 1600, `net_tls_open` 1344,
  `tls13_client_verify_server` 816. The kernel stack is 32 KB, so the worst path is about 10 KB
  plus the callers.
- Under TCG (no `/dev/kvm` in this sandbox), the handshake and the ECDSA and RSA checks all
  complete well inside the 180-second check timeouts.

## Unit tests

`tests/rsa-unit.c` (17 checks), `tests/ecdsa-unit.c` (8 checks, plus 40 random cases),
`tests/x509-verify-unit.c` (about 30 checks), `tests/tls13-*-unit.c` (handshake, record,
server and client units). All pass; the RSA and x509 tests are also clean under ASan and UBSan.
Test vectors are generated by `tests/gen-*-vectors.py` using the Python `cryptography` library.

## Known gaps

- Public internet certificates are not tested. The roots are the 122 built-in ones, but
  they have not been exercised against real sites, and no public site was fetched in the
  test runs.
- SHA-384 and SHA-512 chains and ECDSA-P384 are refused.
- No path length, name constraint, key usage, extended key usage, revocation or policy checks.
- The client Finished is sent before the certificate check. It carries no application data,
  and application keys are released only after the check passes.
- RDRAND is required; there is no fallback.
- Signature verification is not constant-time. It works only on public data.
- No TLS session resumption, no client certificates, no ALPN, no TLS 1.2.
- Not tested on real hardware. The 2010 iMac 11,2 is not covered.
